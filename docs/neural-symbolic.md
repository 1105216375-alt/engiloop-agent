# 从自然语言、报告到受约束的工程符号

本仓库公开的是从桥梁工程产品抽取的实际机制，以及为独立运行新增的接口与合成案例。下面分别说明**原有实现**和**本次新增封装**，不把演示适配器说成已经部署的完整业务链，也不把语义解析成功说成工程事实已经证实。

## 1. 模型和符号系统分别做什么

| 环节 | 模型可以做什么 | 符号系统必须做什么 |
| --- | --- | --- |
| 理解输入 | 在被显式调用时，提出意图、约束、实体、事件、指代等候选 | 限定字段和枚举，检查原文跨度，解析否定/疑似/已修复，保留冲突 |
| 形成任务 | 帮助识别“还扛几年”“剩下谁先修”等表达意图 | 将意图编译成目标、义务、约束和未知项，不能顺手增加用户禁止的导出任务 |
| 计算与推理 | 在允许的接口里提出候选或润色表达 | 运行确定性规则/工具；验证候选引用的证据和数值；仅接受的步骤可更新正式状态 |
| 回答与报告 | 在已允许的事实范围内组织说明 | 对数字、对象、病害、条款等反向核验；错误句删除或保留警示，出口按验证结果决定交付内容 |
| 复用经验 | 不允许把“以前那座桥的答案”搬来当当前事实 | 仅在批准、适用条件和当前证据匹配时复用路线；执行后仍重新验证当前事实 |

这里的符号系统不是一个夹在提示词中的“请遵守规范”，而是程序可检查的数据结构、约束、规则、状态转移与输出门控。它仍然依赖正确的数据、规则及适用范围；不能因此承诺“零幻觉”或免除工程人员复核。

## 2. 两个真实入口，不是一种万能解析器

自然语言入口：

```text
原始文本（保留）
  → 术语、构件、病害、显式尺寸提取
  → SemanticFrame：意图 / 时间 / 范围 / 否定 / 疑似 / 已修复
  → 可选模型提出带原文跨度的候选
  → 符号仲裁：接受、拒绝、保留冲突
  → compile_residual_plan：目标、义务、约束、未知项
```

报告入口：

```text
用户显式提供的 Word 文档
  → 支持的表头、行、构件、病害、尺寸解析
  → 保留报告明示/默认/估计字段的区别
  → 本次新增：绑定文档哈希、表号、行号、描述列及候选来源列
  → 待复核的结构化记录
```

报告表格解析不是把整份报告交给大模型猜一遍；口语意图解析也不是把每一句话硬当成病害表行。它们在业务应用中可以汇合，但两者需要的证据与适配范围不同。

## 3. 为什么必须按这个顺序

1. **先保留输入，再做归一化。** 口语“边梁”“露钢筋”等可以映射到术语，原话仍须保留。归一化后的子句可能不再是原文逐字片段，因此新接口同时返回 `raw_input` 和 `normalized_input`，不会把归一化子句冒充原文的精确字符定位。
2. **先判断断言状态，再进入诊断。** “支座是不是脱空”是问题，“主梁没说有裂缝”是未报告，“修过又裂了”涉及维修与复发；仅识别出“支座+脱空”并不足以诊断。
3. **模型先提出候选，符号系统后仲裁。** 候选必须属于允许字段并能绑定输入跨度。模型不能凭高置信度把疑问变成存在事实，不能把“别出Word”改成导出报告，也不能凭空确认桥名。
4. **先形成执行义务，再选择步骤。** “只比较两年的主梁、不含已修复、不导出报告”会影响范围和执行权限，而不是回答末尾的一句免责声明。
5. **先验证步骤，再更新正式状态。** 执行残差机制的 ACCEPT/REJECT/DEFER/INTERRUPT 不只是标签；拒绝或延后不会把候选结论写入正式已验证事实。
6. **输出仍须核验。** 上游计算对，不代表最终叙述没有换错构件、混错数值、引用不存在的条款。反向核验因此位于输出链，而不只位于检索链。

## 4. 生产源码的抽取边界

| 内容 | 本仓库路径 | 原产品来源与改动 |
| --- | --- | --- |
| 口语归一、构件分句、疾病/尺寸/标度解析 | `engineering_agent/nlp.py` 中标注 Extracted 的函数 | 精确抽取原 `legacy_v7/app.py` 的纯函数；函数逻辑保留。环境城市查询改为不加载私有环境库、返回空值 |
| 全角字符和空白预处理 | `engineering_agent/query_normalizer.py` | 仅抽取原 `QueryNormalizer._pre_normalize`；没有复制生产模型客户端、缓存或配置 |
| 语义框架和约束 | `bip_runtime/semantic_frame.py` | 原生产语义门控与 `compile_residual_plan` |
| 神经候选格式校验 | `bip_runtime/semantic_llm_parser.py` | 原生产实现；模型回调需显式注入，不会自动联网 |
| 神经—符号仲裁 | `bip_runtime/semantic_frame_v2.py` | 原生产 V2；保留 `no_neural_fact_promotion`、冲突与来源字段 |
| Word 表格解析 | `legacy_v7/core/report_parser_v2.py` | 原产品独立解析器，配套实际术语本体 `ontology.py` |
| 独立统一入口 | `engineering_agent/nlp.py:compile_intake` | **本次新增封装**，连接上述真实模块；不加载 Flask 或生产会话 |
| 单条病害的量测追问会话 | `engineering_agent/nlp.py:MeasurementIntakeSession` | **本次新增演示适配**，展示信息缺口如何缩小，不能混称原产品执行控制器 |
| 文档行来源适配 | `engineering_agent/report_input.py` | **本次新增适配**，使用原解析器逐行内存解析，追加来源坐标与审核状态 |

`compile_intake` 的 `semantically_eligible_items` 只表示通过语义层筛选的用户陈述，不意味着系统已经检查过现场照片、量具、报告签章或构件身份。它始终另行声明 `engineering_verified=False`。

## 5. 可复现的养护口语例子

运行：

```bash
python -m examples.semantic_intake
```

所有内容均为合成，不对应实际桥梁。

**第一轮**：“1-1号T梁梁底有一处锈胀露筋。”

实际生产 NLU 提取构件与病害；新会话适配器保留构件编号和所在表面。尚缺具体定位、长度、宽度，因此只追问缺失项。

**第二轮**：“在距0号台6米、距右侧0米的位置，一巴掌长、两指宽。”

定位描述可以规范化，但“一巴掌”“两指”不是量测值。不会换算成某个漂亮的米数，尺寸槽位继续缺失。定位此时也是用户口述，不代表已经和图纸或照片一致。

**第三轮**：“尺子量过：长1.5米，宽十厘米。”

明确数字、明确单位、口述量测动作齐备后，新适配器才能形成简洁记录：

```json
{
  "component": "主梁",
  "component_ref": "1-1号T梁",
  "surface": "梁底",
  "disease": "锈胀露筋",
  "reference_offset": {"reference": "0号台", "distance_m": 6.0},
  "side_offset": {"reference": "右侧", "distance_m": 0.0},
  "length_m": 1.5,
  "width_m": 0.1
}
```

这里 `component` 是归一后的构件类别，`component_ref` 保留具体实例文字，两者不是互相覆盖。裂缝例子则将宽度统一为 `width_mm`，长度仍为 `length_m`。

每个字段附来源轮次、原话片段与证据状态；量测状态为 `user_reported_measurement`，**不是独立验证**。即使文本槽位已经补齐，记录仍“待复核”、`eligible_for_scoring=False`，还保留构件定位、原始照片与量测记录核验缺口。

## 6. “信息缺口”和“执行残差”要分开讲

上例展示的是输入阶段的剩余信息：还差哪些字段、哪些证据。它的价值是引导用户少问、问准、不编尺寸。

产品执行残差位于 `domain/reasoning_bridge.py` 和 `nskernel/dialogue/reasoning`、`nskernel/reasoning`。它跟踪的是未完成目标、约束、未知项、已验证事实和候选步骤的作用。候选步骤需经核验才能改变状态，再重新计算还剩什么；预算、停止、升级和回退也参与执行控制。

两者可以衔接，但不能因为做了几个字段追问就声称已经实现全部执行闭环，也不能把“残差”说成神经网络的训练梯度或数学定理证明。

## 7. Word 报告来源适配如何工作

运行：

```bash
python -m examples.report_intake
```

例子在内存中生成三行 Word 表，然后调用真实解析器。第三行是已修复支座病害，按原解析器规则不进入当前病害记录。

新增来源适配器对每个原表数据行建立仅含表头和该行的内存文档，再交给原解析器。这样即使两行描述完全一样，也不会因字符串匹配而把第二行错绑到第一行。结果中的坐标均为 **从 1 开始** 的表号、行号、列号。

`candidate_source_columns` 表示该字段可能使用的输入列，例如构件列加描述列；它**不是对原解析器每个分支的精确运行时取证**。本次实现了可靠的记录级表行绑定，尚未声称实现任意报告版式下的逐字符、逐公式、逐照片完全溯源。

内容哈希用于同一文档的身份与完整性核对，不证明文档真实。解析器估计的标度继续标为 `estimated`，不能当成报告明示标度，更不能当成合法签发的工程评定结论。

## 8. 已验证与尚未覆盖

公开测试在网络连接被禁用的条件下验证：

- 真正的构件/病害/尺寸解析，不用手填解析结果伪装 NLP。
- 单位换算、跨构件数值隔离、默认标度不冒充用户明示证据。
- 疑似、询问、未报告不进入已确认病害；禁止报告导出约束得以保留。
- 假模型的无原文锚点字段被丢弃，高置信度也不能提升疑问为事实。
- 追问使缺失字段逐步减少；比喻、无单位、未测量、粗估和前后冲突不会自动变成可评分数据。
- 真实 Word 解析器对合成表格工作，重复描述保留独立行坐标，估计字段保持待核状态。

运行本节测试：

```bash
python -m pytest -q tests/test_semantic_intake.py tests/test_report_intake.py
```

必须明确的限制：

- 抽取的历史 NLU 对无单位的“宽0.3”存在默认单位逻辑。低层解析函数保留此行为以忠于原实现；新的量测会话接口更严格，不接受无单位量测。业务接入应使用明确的证据/单位门控，不能直接将低层输出视为可信数值。
- 低层默认尺寸为零表示“未提取”，不是现场实测为零。新的会话接口用缺字段表达未知；合法的定位偏移零仍可以保留。
- 示例追问只面向单条病害，不做任意跨轮省略恢复、跨人称指代、多条病害合并或自动覆盖冲突。遇到冲突保留旧值和冲突记录、要求人工核对。
- 原报告解析器只支持特定表格结构，且会过滤已修复记录；它不能承担完整的维修历史恢复、OCR、图片测量或任意PDF理解。
- 原表格解析器可能按表头习惯使用长度米、宽度毫米；新来源适配器没有重写其单位逻辑，接入真实报告需要核查具体表头与单位。
- 这里的假模型回调只证明接口和仲裁机制，不代表真实模型语义质量、线上成功率或耗时收益。默认不联网；注入真实回调前应取得数据发送授权。
- 私有桥档案、规范全文、生产知识索引、用户/鉴权数据库和模型密钥均不是这些示例的依赖。

工程适用性的来源不是“模型会说专业术语”，而是从输入到状态再到输出都清楚区分：**用户说了什么、系统推断了什么、工具算出了什么、哪些得到核验、哪些仍未知。**
