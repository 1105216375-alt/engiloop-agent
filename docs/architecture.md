# 技术组合与执行顺序

## 一、角色分工

| 层 | 做什么 | 不能越过的边界 |
|---|---|---|
| 模型 / 语义层 | 理解表述、抽取候选字段、提出推理动作、组织语言 | 不自行把缺失数值补成事实，不取得写入与签发权限 |
| 符号层 | 显式对象、量纲、约束、公式、状态、来源和证据能力 | 公式只在适用条件成立时有意义；字段不等于真实 |
| 验证层 | 检查当前已实现的对象、数量、数字、条款、范围及状态条件 | 不以“另一个模型同意”代替证据；未覆盖语义仍可能出错 |
| 残差控制 | 记录尚未满足的义务，决定补什么、保留什么、何时停止 | 不为追求完成而清空未知；不是数学残差收敛证明 |
| 记忆治理 | 提炼已接受过程、审核、按范围检索、影响候选次序 | 不能把历史工程事实复制成本轮结论；回滚步骤不能复用 |
| 审计 / 执行 | 记录尝试、决定、检查点与任务重试 | 日志不是认证；重试不能自动实现外部副作用恰好一次 |

## 二、输入先落到可检查的结构

任务描述与检测报告是独立入口。自然语言入口保留对象、时间、目标和禁止事项；报告入口解析支持的 DOCX 表格并附加文档、表、行、列和原文定位。它们最终可由领域适配器接到统一观察契约，但不是同一个“万能文档模型”。

养护工说“1-1号T梁梁底锈胀露筋，一巴掌长、两指宽”，系统不把比喻转成精确数字。残差列出尚缺的长度、宽度、位置等字段，再追问。补充“长1.5米，宽十厘米”可以确定性归一为 1.5 m × 0.1 m，身份与照片未核实时仍留复核标记。这正是语义候选与工程采信之间的边界。

## 三、当前内核的真实顺序

`LoopManager` 按 priority 排 proposer，先依次调用各 proposer 收集候选，再逐个送入 `VerifierGate`。首个接受的候选交 `MainStateUpdater` 更新状态；拒绝/暂缓继续检查，中断则退出本步候选检查。`RuntimeController` 可继续下一轮，并记录升级建议，不自动交办人工或更换模型；它还执行受覆盖的不变量检查，必要时回退到旧状态并记录事件。

因此：

1. proposer 应只产生候选，不能在 `propose()` 中做不可逆外部写入。
2. 排序不代表廉价候选通过后，昂贵 proposer 就一定没被调用。不能据此编造 token 节省比例。
3. `ACCEPT` 是指定检查器下的执行许可，不是任何命题均已形式化证明。
4. transitions 会保留尝试记录；是否提交必须连同 rollback 决定解读。
5. 缺少证据时桥梁适配允许形成“有条件答复”，不是只有全部目标证明后才能输出任何文字。

## 四、检索与反向核验各做一半

前向检索：根据构件、病害在显式注入的图谱和条款索引中找候选依据。

反向核验：从候选答复中抓取可检查的主张，回到本轮工具结果与条款索引核对。主梁风险数值不能偷用支座的值；不存在条款不能成为依据；条款虽存在但对象/病害不相关时保留警告。公开 `safe_delivery` 校验报告结构、计数及原始答复绑定，异常时不回退裸文本。

这是可执行的防错链，不是整段自然语言的完备证明。软警告与硬拦截有区别；缺索引时公开入口拒绝冒充完整核验。

## 五、过程记忆不是旧答案缓存

真实流程记录 → 提取有唯一 ACCEPT 对应且未回滚的动作 → 候选记忆 → 审核 → 范围/前提匹配 → 为新任务提供候选次序 → 新任务再次校验。

合成实验中，批准的 priority 过程使下一任务从 `risk_assess → priority` 改成 `priority → risk_assess`。新桥的数值仍来自新桥输入；相同主题却缺少当前证据的记忆不可强行应用。这不同于 KV 缓存，也不意味着任何记忆内容都被证明。

## 六、扩展一个领域

实现 `DomainProfile` / `ObservationSchema`，指定原始事实与候选的区别；提供自己的词表、对象标识、规则版本、量纲及证据合同；实现 proposer 和真正有判定能力的 checker；将外部操作放到审批后的提交层；最后用撤证据、改数值、错对象、过期记忆与故障注入验证最终输出。

不要仅修改 prompt 中的“桥梁”为“道路/法律/数学”就声称已迁移。规则有效性、模型输出覆盖范围和制度责任都需重新验证。
